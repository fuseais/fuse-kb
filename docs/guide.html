Technical guide

How fuse-kb finds, ranks, and protects answers from enterprise documents

For engineers and architects evaluating retrieval-augmented generation on HR, Payroll, Finance, IT, and Legal content. Covers the architecture, the search and ranking pipeline, model providers, agent integration, and the security model. For a first run, start with the getting started guide.

Overview

A knowledge base (KB) is a document collection that Fuse has split into passages, tagged, and indexed. fuse-kb is the open-source library that searches KBs from anywhere: a terminal, Claude, or your own agents. It has five parts:

The KB file

One SQLite file with passages, a keyword index, vector embeddings, metadata, and extracted entities.

The search library

Keyword, vector, metadata, and hybrid search with fusion and reranking, plus grounded answers.

Agent surfaces

Tool definitions for the Claude and OpenAI APIs, an MCP server, a CLI, and an agent skill.

Providers

Optional embedders, rerankers, and LLMs: Bedrock, Anthropic, OpenAI-compatible, Ollama, or local models.

Backends

A common interface so the same tools work with downloaded files and hosted Fuse knowledge bases.

Everything beyond keyword search is opt-in. With no providers configured, fuse-kb makes no network calls at all.

Architecture

Fuse handles ingestion: extracting text and tables, tagging passages, and building the indexes. fuse-kb handles retrieval wherever the KB ends up.

Inside a knowledge base

A KB file is a standard SQLite database with three retrieval levels in one file. The full specification is in FORMAT.md.

TableWhat it holdsUsed for
chunksPassage text, document and page, source, category, domain, jurisdictionResults, citations, metadata filters
chunks_ftsSQLite FTS5 index, Porter stemmingKeyword search (BM25)
chunks_vecOne embedding per passage (sqlite-vec)Search by meaning
entitiesExtracted people, organizations, dates, amounts, form numbersAnswer hints, analysis
_metaBuild details, including embed_spec: the model that made the vectorsChoosing the query embedder

Fuse extracts tables as Markdown grids, so values stay attached to their row and column labels ("Gold Plan | Monthly fee | $630"), which matters for questions about figures.

How search works

fuse-kb offers four search modes. Hybrid is the default and the right choice for most questions.

ModeHow it worksBest for
hybridKeyword and vector candidates combined with Reciprocal Rank Fusion, optionally rerankedMost questions
lexicalBM25 keyword ranking; phrase matches an exact phraseNames, form numbers, codes, IDs, exact wording
denseNearest neighbors of the question's embeddingParaphrased questions with no shared keywords
filterMetadata only, in document and page order"What documents do we have about…" inventories

The hybrid pipeline

Keyword search treats any shared word as a match and lets BM25 rank passages that share more, and rarer, words higher. Requiring every word would make natural-language questions match nothing. If the vector embedder isn't available, hybrid search runs on keywords alone and says so in the result's notes.

Ranking: RRF and reranking

Reciprocal Rank Fusion

RRF merges rankings without comparing their incompatible scores. Each passage earns 1 ÷ (k + position) from every list it appears in, counting the top position as 0, and the points are added. Passages near the top of several lists win.

The constant rrf_k (default 60) sets how much the very top positions count. Passage A is 1st for keywords but 25th for vectors; passage B is 8th in both:

rrf_kABWinner
100.1290.118A: one standout ranking counts for a lot
200.0730.074B, narrowly
600.0290.030B: agreement between rankings counts more

Use a low rrf_k (around 10) when a single exact match should win, as with form numbers or contract clause references. Keep 60 or raise it when you trust passages that both searches agree on.

Reranking and the final order

A reranker reads the question together with each of the top 20 passages and scores relevance from 0 to 1. The fusion setting decides how that score is used:

fusionFinal orderPrefer for
rerank (default)The reranker's orderConversational questions where relevance is a judgment call
rrfThe reranker's ranking fused with the keyword and vector rankingsCodes, form numbers, statute and policy references, amounts

With rrf, a passage that matches an exact term strongly isn't dropped on one reranker judgment. Each result carries rank_rrf and rank_rerank, so you can see how far reranking moved it.

Research and answers

research()

research() tries strategies in order and keeps the first convincing result: hybrid with HyDE (when an LLM is configured), then plain hybrid, then keyword only. A result is convincing when its best rerank score reaches 0.3. Without a reranker, the first strategy that finds anything wins. The result reports strategy and every attempt.

HyDE

Hypothetical Document Embeddings: an LLM writes a short passage that would answer the question, and vector search uses that passage instead of the question. It bridges wording gaps ("time off after having a baby" versus "parental leave"). Keyword search and reranking still use the original question.

answer()

answer() runs research(), then asks the configured LLM to answer from the retrieved passages only. Answers cite passages as [1], [2], copy figures exactly as written, and reply with a fixed sentence when the passages don't cover the question, reported as no_answer: true. Answer style is yours to choose: most applications let their own agent write the final answer from search results.

Providers

Every provider is optional and selected with a short spec string, or passed as your own object implementing one method.

Embedders: chosen by the KB

Vectors can only be searched with the model that made them, so each KB records its embed_spec and fuse-kb selects that embedder automatically. A spec read from a file can only name a built-in provider, never custom code.

Agent integration

Toolkit turns a library of KBs into tool definitions and runs the calls. The definitions follow your configuration: KB names become an enum, and reranking and HyDE options appear only when they can work.

from fuse_kb import KBLibrary, Toolkit

toolkit = Toolkit(KBLibrary("kbs/", reranker="cohere"))
tools = toolkit.anthropic_tools()          # or toolkit.openai_tools()
result = toolkit.call("kb_research", {"kb": "handbook", "question": "..."})
ToolPurpose
kb_listLists KBs with descriptions, so the agent can choose
kb_researchThe default: hybrid search with automatic fallbacks
kb_searchOne explicit mode, with phrase, fusion, rrf_k, and hyde options
kb_read_pagesUp to 6 consecutive pages, for tables or lists cut off at a passage edge
kb_documentsLists a KB's documents
kb_answerGrounded answer with citations (only with an LLM configured)

MCP: fuse-kb mcp --path ./kbs serves the same tools over stdio to Claude Desktop, Claude Code, and other MCP clients, or over HTTP with --transport streamable-http.

Skill: fuse-kb skill --install ~/.claude/skills installs instructions that teach an agent the search workflow, how to read scores, how to cite, and to treat passage text as data.

Hosted backends

The tools talk to a small interface, KBBackend: info, documents, search, research, pages, answer, close. A local file is one implementation; a hosted Fuse knowledge base is another. Register any backend in a library, and it appears in every tool next to local files:

library = KBLibrary("kbs/")
library.add("finance-policies", hosted_backend)   # same tools, same result shape

Results use the same Hit shape everywhere, so citations and scores read the same way when an evaluation moves from a downloaded file to a production backend.

Security model

Enterprise document collections come from many authors, vendors, and systems. fuse-kb assumes any document may be hostile and defends each path by which one could cause harm.

ThreatDefense
Instructions hidden in a document steer the model (prompt injection)Hidden markup and sentences addressed to an AI are removed before any LLM sees a passage; Fuse also removes them at ingestion. Passages are delimited and marked untrusted, and delimiter look-alikes are neutralized.
An agent acts on injected textSearch results carry a warning on suspicious passages; tool descriptions, MCP instructions, and the skill tell agents never to follow passage text.
Ingestion rewrites contentFuse accepts an LLM's cleaned text only if it adds no links or contact details and keeps every number; otherwise the extracted text is kept.
A KB file runs codeFiles can only name built-in providers; custom classes load only from your own code or configuration.
A file is modifiedFiles open read-only and immutable; decrypted files are read-only in memory.
An agent reaches other filesKBs are addressed by name, and only names discovered on the configured path resolve.
SQL injection through filtersFilter columns come from a fixed list; values are always bound parameters.
A copied file is readOptional PGP encryption with customer-held keys, decrypted only in memory.
Detection is heuristic. Removing instruction-like text stops common attacks and is tested against known phrasings without flagging normal policy language, but no filter catches every novel phrasing. The defenses are layered for that reason: removal, untrusted framing, grounded-answer rules, and agent warnings. Treat model output as advice, and keep actions with consequences (payments, account changes) behind human approval.

Encrypted files

A .sqlite.gpg file opens like any other KB. GnuPG decrypts it to memory, and SQLite reads it from there, so no readable copy touches disk. The key comes from your GnuPG keyring, or for servers from FUSE_KB_PGP_KEY or FUSE_KB_PGP_KEY_FILE with FUSE_KB_PGP_PASSPHRASE; an injected key lives in a temporary RAM keyring that is deleted after use. Requires GnuPG and Python 3.11+. Setup and key handling are covered in Handling KB files safely.

Evaluating RAG on your documents

A short, repeatable evaluation tells you more than any benchmark:

  1. Write 20 to 50 real questions from the people who will use the system, each with the document and page that answers it. Include figures, dates, and exact-term questions, plus a few the KB can't answer.
  2. Measure retrieval first. For each question, check whether the right page appears in the top 5 results. Answer quality can't exceed retrieval quality.
  3. Compare settings: with and without a reranker, fusion rerank versus rrf, and rrf_k at 10 and 60. Exact-term heavy content (Legal, Payroll) often favors rrf.
  4. Then judge answers: correct, cited, figures exact, and an honest "not found" for unanswerable questions.
  5. Include hostile documents in a test KB to confirm injected instructions don't reach answers.

Use --json on any CLI command to script the evaluation.
